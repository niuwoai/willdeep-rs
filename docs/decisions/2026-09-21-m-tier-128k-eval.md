# ADR：M 档降到 128K 能否完整可用——评测需求（2026-09-21）

> 状态：提议（待评测） | 基于 develop @ v0.79.0-rc3 | 关联：`docs/MODEL_TIERS.md`、`docs/MODEL_EVAL.md`、`bench/model-eval/`

## 背景

`docs/MODEL_TIERS.md` 定的部署基线 M 档是 256K，`implementer`（最多 16 个声明写入路径）和路由规则「装不进 256K 才申请 L」都按 256K 设计。但立项时 128K 和 256K 被当成同一个「开源主流窗口」区间，**从没分开比过**。

这个缺口是 README 暴露的：0.78.0-rc29 把「适合谁」写成了「机房里只有 32K 和 128K 两档模型」，等于向私有化用户承诺 128K 也能完整跑。0.79.0-rc2 已把 README 改回与设计一致的「32K–64K 和 128K–256K 两段」，但真正的问题还悬着：

- 很多开源权重原生只有 128K，256K 靠 YaRN 等外推，长尾位置质量打折扣；
- 128K 的 KV cache 约为 256K 的一半，私有化采购门槛差一截；
- 如果 128K 做 M 档也能完整可用，README 可以把适用面说得更宽；如果不能，就要写清「M 档至少 256K」或给出 128K 下的降级配置。

## 要回答的问题

1. M 档窗口为 128K 时，`implementer` 的任务完成率与 256K 相比掉多少？
2. 掉在哪：上下文装不下（压缩 / 截断触发）、拆分变多，还是被迫申请 L？
3. 128K 下「最多 16 个声明写入路径」是否要下调，下调到多少完成率回到可接受？
4. 同一模型原生 128K 与外推到 256K，哪个在 M 档任务上更好？（回答「机房里该不该开外推」）

## 评测设计

- **变量**：M 档 `context_window` 取 131072 与 262144 两组，经 `[subagents.implementer] context_window` 显式覆盖；S 档固定 48K；**L 档关闭**，模拟 air-gapped 机房。
- **模型**：至少一个开源权重模型（候选 GLM、Qwen、DeepSeek 开源版），两组用同一模型同一端点，只改窗口。第 4 问另加一组「同模型开外推」。
- **任务集**：现有 `bench/model-eval/` 20 个任务都是单文件小改，压不到窗口，不能直接用。新增 `bench/model-eval/tasks-m-tier/`，8–12 个多文件任务，按「读入材料量」分三段：约 40K、约 100K、约 180K token（后者在 128K 下必须拆分或消化）。每个任务带确定性验证命令，裁决只看退出码，与现有任务集一致。
- **每组每任务跑 3 次**，取中位数，减小随机性。

## 指标

| 指标 | 来源 |
|---|---|
| 验证通过率 | 验证命令退出码 |
| 上下文压缩 / 截断次数 | 会话记录 |
| 派工拆分次数、Worker 数 | `agent-metrics` |
| L 档申请次数（关闭状态下即「无路可走」次数） | Runtime 路由日志 |
| 总 token 与墙钟时间 | 会话记录 |

报告按惯例输出 JSON + Markdown，脚本扩展 `scripts/model_eval.rb`，不另起一套。

## 判定标准（预设，跑之前定死）

- 128K 组通过率不低于 256K 组的 90%，且约 180K 段任务能靠拆分 / 消化完成：**128K 可作 M 档下限**，README 与 `MODEL_TIERS.md` 写明「M 档 128K 起」。
- 否则：`MODEL_TIERS.md` 写明「M 档至少 256K」，并给出 128K 机房的降级配置（下调写入路径上限、默认开 `task.digest_oversized`），README「适合谁」同步。

## 不做的

- 不在这次评测里调提示词或路由规则；只改窗口这一个变量。
- 不评前沿闭源模型；私有化场景用不上。

## 后果

- 评测跑完后本 ADR 状态改为「已裁决」，结论回写 `docs/MODEL_TIERS.md` 部署基线表和 README「适合谁」，并同步 Xedit 设计文档 §10.6 的镜像。
