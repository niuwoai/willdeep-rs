# some.im 集成

some.im 是 WillDeep 的一等 Provider：除了标准的模型调用，还额外提供联网搜索、纯文本模型的视觉回退，以及浏览器登录。

## 快速上手

```bash
export SOMEIM_API_KEY="<your-key>"

willdeep \
  --provider some-im \
  --model glm-5 \
  --workspace ~/Sites/project \
  "检查当前仓库并修复测试"
```

或写入 Profile：

```toml
[providers.some-im]
provider = "some-im"
api = "chat-completions"
api_base = "https://some.im/v1"
api_key_env = "SOMEIM_API_KEY"
model = "glm-5"
vision_model = "qwen3-vl-plus"
context_window = 131072
```

## 登录

推荐用浏览器登录，免去手工复制 Key：

```bash
willdeep --onboarding
```

选择 `1) some.im 浏览器登录（推荐）`，终端会打印登录 URL 和设备码，浏览器授权后 CLI 自动取回 API Key 并写入 `0600` 权限的配置文件。完整流程与 `WILLDEEP_CLIENT_LOGIN_SECRET` 的作用见 [认证与凭据](AUTHENTICATION.md)。

## 自动识别

`--provider auto`（默认）按 API Base 的 **host 精确匹配**识别 Provider，识别为 some.im 的 host 只有三个：

- `some.im`
- `api.some.im`
- `api.niuwoai.com`

匹配是精确相等而非后缀匹配，所以 `https://some.im.example/v1` 会被归为 `openai-compatible`。显式传 `--provider some-im`（或在 Profile 里写 `provider = "some-im"`）会跳过域名推断。

国内线路可以显式指定：

```bash
export WILLDEEP_API_BASE="https://api.niuwoai.com/v1"
```

`--provider some-im` 在未指定 API Base 时默认使用 `https://some.im/v1`，默认 Root 模型为 `glm-5`。1M 的 `deepseek-v4-flash` 只作为通过升级票据后的 Deep 档使用。

## 请求头

some.im 请求使用 Bearer 鉴权，并额外附带两个上下文头：

| Header | 说明 |
|---|---|
| `Authorization: Bearer <key>` | API Key |
| `x-willdeep-session-id` | Provider 实例级随机 UUID |
| `x-willdeep-workspace-id` | Provider 实例级随机 UUID |

这两个 ID 在 Provider 配置构造时各生成一个 UUIDv4，**与 WillDeep 的会话 UUID、工作区路径都没有关系**，纯粹是用于关联同一次运行请求的匿名标识，不含任何本地路径。视觉回退模型和廉价子 Agent 模型因为复用同一份 Provider 配置，会共享这对 ID。

当 some.im 中转提供 Anthropic Messages 线格式时，鉴权仍使用 Bearer（而不是 `x-api-key`），并照常带上这两个头。

## 视觉回退

some.im 的部分主力模型只接受文本。当主模型属于纯文本模型而消息里带了图片时，WillDeep 会用**同一个 API Base、同一把 API Key** 调用视觉模型描述图片，只把描述文本交给主模型。

被判定为纯文本的模型（按模型名小写后判断）：

- 名字含 `deepseek` 且不含 `vl`；
- 以 `someim-auto` 开头；
- 以 `someim-coding` 开头。

默认视觉模型为 `qwen3-vl-plus`，可用 Profile 的 `vision_model` 覆盖：

```toml
[providers.some-im]
vision_model = "qwen3-vl-plus"
```

行为细节：

- 只处理**当轮新用户消息**里的图片，不回溯历史；
- 视觉模型调用不带任何工具；
- 描述以 `[Image description generated by ... for N attached image(s)]` 的形式追加到用户消息正文，随后图片附件被移除，非图片附件保留；
- 视觉调用强制使用 Chat Completions 线格式。

## web_search

`web_search` 工具只在 Provider 为 some.im 时启用，未配置时报错 `web_search requires a some.im provider`。

| 项目 | 值 |
|---|---|
| 端点 | `POST {origin}/api/v1/customer/web-search` |
| 鉴权 | 与模型调用同一把 Bearer Key |
| 请求体 | `{"query": ..., "count": 1..20（默认 8）, "provider": "auto"}` |

注意端点是**替换整个路径**后拼出来的：`https://some.im/v1` 的搜索端点是 `https://some.im/api/v1/customer/web-search`，不挂在 `/v1` 下面。

搜索请求不携带 `x-willdeep-session-id` / `x-willdeep-workspace-id`（那两个头只在 Provider 层添加）。

`web_search` 在**所有审批模式**下都需要逐次确认，且不提供 Always Allow。

`web_fetch` 是独立实现，不走 some.im，也不使用 API Key。其安全约束见 [审批与自动化](APPROVALS.md)。

## 子 Agent 的廉价模型

Provider 为 some.im 时，七个托管窄工种自动绑定各自的 `someim-32b-<trade>`，未托管工种回落 `glm-5`；`implementer` 使用 GLM-5，`deep` 推荐显式绑定 `deepseek-v4-flash`。可以在 `[subagents.*]` 中显式覆盖，见 [子 Agent 与后台任务](SUBAGENTS.md)。

## 上下文压缩模型

Provider 为 some.im 时，手动 `/compress` 与自动压缩的摘要调用绑定网关托管的 `someim-32b-compressor`（当前落在 `deepseek-v4-flash`，按 flash 档计费）：固定压缩指令存在服务端并以 replace 模式注入，客户端只发裸转录——压缩把整段旧历史重发一遍，是循环里最大的单笔固定开销，压缩指令的迭代也因此不再依赖客户端发版。`[agent] compressor_model` 可覆盖；覆盖成非托管模型时，行内压缩指令仍随请求携带。其它 Provider 未配置时维持旧行为（会话模型 + 行内指令）。

## 会话标题模型

**标题不绑网关别名，所有 Provider 一律默认取会话模型。** 这是与判官、压缩器不同的一条，
理由有两条：网关侧没有为标题托管的职能模型，而 `/v1/models` 不列虚拟模型链——想确认某个
`someim-*` 档存不存在只能逐档发最小请求探活，凭猜测钉一个别名等于埋一个"某天静默失效"的默认值；
`deepseek-v4-flash` 虽然按 flash 档计费，但它在 [模型三档](MODEL_TIERS.md) 里是稀缺的 L 档，
拿 1M 窗口写一行标题与那份文档的口径直接打架。

代价是可控的：标题请求只在会话**第一轮**发一次，载荷是一问一答各截断到 800 字，
与对话长度无关。要换便宜档写 `[agent] title_model`；整条关掉写 `[agent] auto_title = false`，
标题会停在第一条提示词的确定性派生，仍然可读。详见 [会话标题](TUI_GUIDE.md#会话标题怎么来的)。

## 错误脱敏

Provider 返回的错误体在进入日志或界面前会替换 `Bearer `、`sk-`、`api_key":"` 三类标记以及 Key 原文为 `[REDACTED]`，并截断到 8 KB。
